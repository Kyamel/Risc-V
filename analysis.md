# RISC-V Pipeline Implementation Analysis Report

## Executive Summary

After thorough analysis of your RISC-V pipeline implementation, I've identified several critical issues that explain the incorrect simulation results. The main problems are architectural inconsistencies, improper signal connections, and missing pipeline control logic.

## 1. Critical Issues Found

### 1.1 Major Architectural Problems

#### **Issue A: Broken Control Unit Connection**
**Location**: `src/core/rv32i_cpu.v`, lines 139-142
```verilog
// Control Unit
control_unit control_unit (
    .instruction(if_id_instruction),
    .control_signals(id_ex_control_signals)  // WRONG!
);
```

**Problem**: The control unit is connected directly to the ID/EX register output instead of being properly integrated into the ID stage. This bypasses the entire decode stage and causes control signals to be generated for the wrong instruction.

**Impact**: Control signals are always one cycle behind, causing incorrect ALU operations and memory accesses.

#### **Issue B: Missing Pipeline Register Integration**
**Location**: Multiple files
**Problem**: The `pipeline_registers.v` module exists but is never instantiated in the main CPU. Instead, each stage manually implements its own pipeline registers, leading to inconsistent behavior.

#### **Issue C: Incorrect Flush Logic**
**Location**: `src/stages/if_stage.v`, `src/stages/id_stage.v`
**Problem**: The flush signal is generated by the EX stage but never properly connected to IF and ID stages, so branch mispredictions aren't handled correctly.

### 1.2 Signal Connection Issues

#### **Issue D: Branch/Jump Logic Disconnected**
**Location**: `src/core/rv32i_cpu.v`
**Problem**: Branch detection logic exists in `ex_stage` but the `flush` signal is never connected to pipeline stages.

```verilog
// Missing connections:
wire flush;  // Declared but never assigned
wire [31:0] new_pc;  // Never properly connected to branch unit
```

#### **Issue E: Forwarding Unit Not Connected**
**Location**: `src/stages/ex_stage.v`, lines 71-84
**Problem**: The forwarding logic exists but receives wrong data sources:
```verilog
case (forward_a)
    2'b01: forwarded_rs1 = mem_wb_mem_data;      // Should be ex_mem_alu_result
    2'b10: forwarded_rs1 = mem_wb_alu_result;    // Should be mem_wb_data
```

### 1.3 Memory Interface Problems

#### **Issue F: Memory Access Timing**
**Location**: `src/stages/mem_stage.v`
**Problem**: The memory interface logic is overly complex and doesn't properly handle byte/half-word accesses. The `read_data` signal processing happens in wrong clock domain.

#### **Issue G: Instruction Memory Interface**
**Location**: `src/memory/instruction_memory.v`
**Problem**: Mixed synchronous/asynchronous logic causes timing issues:
```verilog
// Synchronous read but used as combinational
always @(posedge clk) begin
    if (reset) begin
        data_out <= NOP;
    end else if (read_en) begin
        data_out <= mem[addr[31:2]];  // Should be combinational for IF stage
    end
```

## 2. Unused/Redundant Signals

### 2.1 Completely Unused Signals
- `src/control/stall_controller.v` - Entire module unused
- `src/components/branch_unit.v` - Entire module unused  
- `src/components/pc_generator.v` - Entire module unused
- `src/core/pipeline_registers.v` - Entire module unused
- `debug_stall`, `debug_flush` in `rv32i_cpu.v` - Never assigned

### 2.2 Redundant Logic
- Branch resolution logic duplicated between `ex_stage.v` and `branch_unit.v`
- PC calculation logic duplicated between `if_stage.v` and `pc_generator.v`
- Multiple unused control signal bits in `constants.v`

## 3. Pipeline Hazard Issues

### 3.1 Data Hazards
**Problem**: Load-use hazards aren't properly detected because:
1. Hazard detection unit is instantiated but `stall` signal is hardcoded to `1'b0` in many places
2. Forwarding paths are incorrect (wrong data being forwarded)

### 3.2 Control Hazards  
**Problem**: Branch prediction is non-existent and flush logic is broken:
1. Branches are resolved in EX stage but flush doesn't propagate properly
2. No branch predictor, causing unnecessary stalls

## 4. Simulation Result Analysis

Looking at your simulation output:
```
Ciclo |   PC   | Instrução  | ALU Res | WB Data  | RD
    2 | 0000000c | 00000013 | 00000001 | 00000000 | x 0  // Should write to x1
    3 | 00000010 | 00102023 | 00000000 | 00000001 | x 1  // Delayed by 1 cycle
```

**Root Cause**: Control signals are delayed by one cycle due to incorrect control unit connection, causing:
- Instructions execute with wrong control signals
- Register writes happen for wrong instructions
- Memory operations use incorrect addresses

## 5. Specific Fixes Required

### 5.1 Immediate Fixes
1. **Fix Control Unit Integration**:
   - Move control unit into ID stage
   - Connect instruction from IF/ID register
   - Generate control signals in decode stage

2. **Fix Pipeline Registers**:
   - Either use the existing `pipeline_registers.v` module properly
   - Or remove it and fix the individual stage registers

3. **Connect Hazard Detection**:
   - Connect stall signals properly throughout pipeline
   - Implement proper load-use hazard detection

### 5.2 Architecture Improvements
1. **Simplify Memory Interface**:
   - Make instruction memory purely combinational
   - Simplify data memory byte-enable logic

2. **Fix Forwarding Logic**:
   - Correct the data sources for forwarding
   - Add forwarding from MEM to EX stage

3. **Implement Proper Branch Handling**:
   - Connect branch unit or integrate into EX stage
   - Implement proper flush propagation

## 6. Proposed Refactored Architecture

I recommend restructuring the top-level module to have clearer separation of concerns:

### 6.1 New Top-Level Structure
```verilog
module rv32i_cpu (
    // External interfaces...
);
    // Pipeline stage connections
    wire [31:0] if_pc, if_instruction;
    wire [31:0] id_pc, id_instruction, id_rs1_data, id_rs2_data, id_imm;
    wire [31:0] ex_pc, ex_alu_result, ex_rs2_data;
    wire [31:0] mem_pc, mem_result, mem_data;
    wire [31:0] wb_pc, wb_data;
    
    // Control signals
    wire [`CONTROL_SIGNALS_WIDTH-1:0] id_control, ex_control, mem_control, wb_control;
    
    // Hazard control
    wire stall, flush, branch_taken;
    wire [31:0] branch_target;
    wire [1:0] forward_a, forward_b;
    
    // Stage instantiations with proper connections...
endmodule
```

### 6.2 Recommended Module Changes
1. **Integrate control unit into ID stage**
2. **Simplify memory interfaces**  
3. **Use single pipeline register module**
4. **Add proper hazard detection integration**
5. **Implement branch predictor (simple predict-not-taken)**

## 7. Priority Order for Fixes

1. **CRITICAL**: Fix control unit connection (causes all wrong behavior)
2. **HIGH**: Connect hazard detection and stall logic
3. **HIGH**: Fix forwarding data sources
4. **MEDIUM**: Simplify memory interfaces
5. **LOW**: Clean up unused modules
6. **LOW**: Add branch prediction

The current implementation has solid individual components but suffers from integration issues. The main problem is that the control flow isn't properly pipelined, causing a cascade of timing problems throughout the design.
